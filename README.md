# Canonical patient data model — PAI3 practical test

A governed patient data foundation for a concierge medical practice: twenty-two canonical
entities in Python and Pydantic v2, with provenance, validation, and an AI layer that can
read the record but cannot write to it.

```bash
python3.12 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/pytest -q          # 271 tests
.venv/bin/ruff check src tests mock
.venv/bin/python scripts_build_d3.py   # regenerate the example patient record
.venv/bin/python scripts_normalise.py  # run the optional normalisation build
.venv/bin/python scripts_run_ollama.py # D8 against a real local model
.venv/bin/python scripts_audit_dimensions.py   # every required dimension, checked
```

`scripts_audit_dimensions.py` is the one to run before trusting anything else here. It checks the
brief's 25 required dimensions against D2's map, every identifier D2 names against the code, and
every entity D2 names against the example record — and exits non-zero on any gap. It found five
entities that existed in code and were missing from the example, and one field the design document
named that the code does not have.

The design document, `docs/model_design.md`, is the specification. Where it and this README
differ, the design document is correct.

## Which parts ran on a real model, and which did not

Stated here rather than left to be inferred, because the artifacts look alike and only one of
them is evidence of inference.

| | Generator | `engine` | What it is |
|---|---|---|---|
| `deliverables/d3_example_patient.json` | `StubGenerator` | `stub` | **No inference ran.** Claims are built deterministically so the record is byte-reproducible |
| `tests/test_d8_previsit_brief.py` | `StubGenerator` | `stub` | Same, so the suite is deterministic and needs no model |
| `deliverables/d8_real_inference/` | `OllamaGenerator` | `ollama` | A real call to a model on this machine. `run.json` records the engine version, the elapsed time and the verdict |

`Engine.STUB` exists for exactly this reason. An earlier version of the stub reported
`engine=ollama` with `model_id=llama-3.3-70b-instruct` and a genuine SHA-256 prompt digest —
of a prompt that was never sent anywhere, for a model that was not even installed. In a
submission about provenance, that artifact was the one piece of unverifiable provenance in it.
A stub now says it is one, in the artifact, where a reviewer cannot miss it.

**What the real run found.** Running `qwen2.5:7b` locally produced a defect reasoning had not:
the model restated lab values in its prose and left the structured `values` list empty, so
checks 2 and 3 had nothing to compare and an artifact carrying unverified numbers passed. A
sixth check closes it — a claim stating a decimal must declare it — and the same model, same
prompt, same temperature, has since been both rejected and accepted by it across runs. The
guardrail is what makes that variance survivable instead of silent.

Wiring it took one protocol and two implementations; the adapter does not know which answered.
One thing had to change beyond the generator, and the previous docstring was wrong to claim
otherwise: the prompt used to be assembled *after* generation purely to be hashed, which is
fine for a stub and wrong the moment a model needs to receive it.

## How the model is structured

**Three layers, with a one-way dependency.**

| Layer | Holds | Written by |
|---|---|---|
| Source | The PDF, spreadsheet, EMR export as received, with a content hash | Nobody — immutable |
| Canonical | Accepted clinical fact. 22 entities | Humans and source systems |
| AI | Summaries, extraction candidates | The AI layer only |

The rule is that **AI never writes to the canonical layer**. Not because its output is poor,
but because once written an AI-produced value is indistinguishable from a physician-entered
one: there is nothing to roll back to and nothing to show in an audit.

That rule is a dependency direction, so it is checkable rather than a promise:

```bash
grep -rn 'from pai3\.ai' src/pai3/entities src/pai3/values src/pai3/base.py \
    src/pai3/validation.py src/pai3/lineage.py src/pai3/interpretation.py
# no matches
```

**Three base tiers**, and the class an entity inherits from is a statement about the data:

```
CanonicalRecord   id, provenance, record_status, version, created/updated, updated_by
  └ PatientScoped   + patient_id
      └ ClinicalRecord  + encounter_id
```

`Patient` is not `PatientScoped` — its own id is the scope. `Provider` is not either, and
that is governance rather than tidiness: a provider record is not covered by any patient's
consent and is not part of a patient data export.

A single universal base would have given nine of twenty-two entities a nullable
`encounter_id` they never set. `Consent` and `Goal` have no encounter; `Encounter` *is* the
encounter.

**No entity can be deleted.** `record_status` has `active`, `superseded` and
`entered_in_error`, and no `deleted`: removing an erroneous record removes the reason a
physician prescribed something while the prescription remains.

Entity files are grouped by what changes together rather than one per entity —
`clinical.py` holds the coded statements, `results.py` the things with a `Quantity`,
`therapy.py` the things with a dose.

## How validation works

Two layers, and the difference decides whether a record exists at all.

**Layer 1 — structural invariants, enforced by Pydantic.** The record is never created. It
stays in the source layer and the flag attaches to the *document*. A lab with no analyte
name is not a lab result; one with no collection date cannot be trended or placed on a
timeline.

**Layer 2 — data quality, raised as `DataQualityFlag` records.** The record exists in
canonical, visible and citable, and carries a flag saying what is wrong. A lab with a value
and no unit lands here, because D5 says *missing units must trigger review* — review, not
reject. Rejecting it would make the lab invisible: present in the source layer, absent from
every brief and every trend, and unseen by the person who has to resolve it.

Severity has four classes, and **`blocking` does not block persistence — it blocks
autonomous conclusion.** The record is readable and citable; no read-model and no agent may
assert from it without surfacing the flag.

The invariant underneath all of it:

> **Canonical never holds a value nobody vouched for.**

Not "canonical is always complete". An unresolved conflict leaves the field empty with a
blocking flag naming both candidates, which is why `LabResult.quantity` is optional. A
physician sees *"glucose — conflict between EMR 5.5 and lab 7.2, unresolved"* rather than a
silently chosen winner. Selecting the newer source automatically is forbidden: recency is a
heuristic, not a vouching.

`DataQualityFlag` is an entity rather than a list on each record, for three reasons: the
review queue is a cross-patient query; a conflict exists *between* two records and needs two
targets; and a flag's lifecycle is independent of the clinical record's version, so
embedding would bury change history under review noise.

## How provenance is represented

`Provenance` is embedded on every canonical record, and it is a property of a **value**.
`AuditEvent` is a stream of events over a **record**. Conflating the two is the most common
failure in models of this kind.

```python
Provenance(
    origin=ProvenanceOrigin.AI_EXTRACTION,   # human | source_system | ai_extraction
                                             # | ai_inference | system_derived
    asserted_by=accepting_clinician,         # who vouched — a person, for an accepted extraction
    asserted_at=...,
    source_refs=[source_reference_id],       # → SourceReference → page, field, span, quote
    derived_from=[],                         # canonical records this was reasoned from
    depth=0,                                 # 0 = straight from a document
    extraction_confidence=0.91,
)
```

Three things are worth knowing.

**`ai_extraction` and `ai_inference` are separate**, because the second compounds. A fact
inferred from other canonical facts can grow derivatives, and `ai_inference` is capped at
`depth <= 1`: AI may reason from documents and from first-generation facts, never from its
own inferences. Retracting a record raises `PARENT_RETRACTED`, severity blocking, on every
record that named it in `derived_from` — the derived fact may still be true, but its basis
is gone.

**There is no `review_status` field.** D4 asks for human review status and it is absent
deliberately: AI never writes to canonical, so canonical cannot by construction hold
unreviewed AI content. The capability lives in three places that already exist — open
`DataQualityFlag` records say what is outstanding, `provenance.asserted_by` says who
vouched, and `AuditEvent` says when it was accepted and from which candidate. Derived beats
stored here, because a stored flag diverges from reality the moment a flag is resolved and
the field is not updated with it.

**Field-level provenance is a short whitelist, not a map.** `dose` and `status` on
medications, `quantity` on results, `clinical_status` on conditions — the fields where two
sources actually disagree. A rule of "wherever it differs" grows the map to twenty fields
within a week.

## How an AI agent reads from the model safely

Four things stand between an agent and the record, and each is a type rather than a
convention.

**1. It cannot read without consent.** Every projection function takes an `AIReadScope`, and
no overload takes a bare `patient_id`. The only way to obtain one is `authorize_ai_read`,
which raises rather than returning `None` — so refusal is the default path, not something a
caller must remember to check. The token is frozen and is never persisted: a stored
capability is a forgeable one.

This gates the AI path only. A physician reading a chart needs `treatment` consent under
different rules including break-glass, and **this model does not build general access
control.**

**2. It never receives identity.** The projection emits `AIPatientView` — `patient_id`, age
and sex — and the type has no field for a name, an MRN, an address or a date of birth. "The
model saw the patient's name" is unexpressible, not discouraged. Age replaces the birthday
because dosing and reference ranges need an age.

**3. Every span of text arrives labelled.** `ClinicalText` carries a `TextOrigin`, and the
boundary is whether the text crossed the practice perimeter rather than who signed the
record holding it: a physician who pastes a patient's message carries external text inside,
and their signature does not change what the text is. `unknown` counts as external — the
default fails closed. There is deliberately **no `sanitized` flag**: the schema makes the
source class of every span legible, and declining to act on instructions found in an
external span is a policy of the AI layer, not a property of the schema.

**4. Nothing is dropped silently.** The projection reports what the context budget left out,
with a reason, in a required field. Allergies, active medications, active conditions and open
blocking flags are non-droppable: if they alone do not fit, **the budget is wrong, not the
allergies**, and the generation is refused rather than truncated. The physician then receives
the deterministic brief — which has no budget and holds every lab — plus a statement of why
there is no narrative.

On the way out, six checks run before a generation becomes an artifact:

| | Check |
|---|---|
| 1 | Every citation appears in `inputs` — a citation to a record never read is fabricated |
| 2 | Every asserted number matches the record it cites |
| 3 | No claim asserts a value for a record whose value slot is empty |
| 4 | Open blocking flags on the inputs appear in the output |
| 5 | No non-droppable record appears in `omitted` |
| 6 | A claim stating a number declares it in `values`, or checks 2 and 3 have nothing to compare |

All of this depends on the output being structured. Over free prose none of the checks works:
a number extractor that misses one produces a false pass, which is worse than no check. So an
`AISummary` is a list of claims, each carrying its citations and its numbers.

Two honest limits. These verify **grounding, not judgement** — a claim can cite the right
record, carry the right number, and still be a poor clinical inference, and the only check on
judgement is human review. And they are **asymmetric: they catch fabrication, never
omission.** A brief that failed to mention a critical allergy passes all six, because there
is nothing to diff a summary against that was never written.

## What the agent may not modify

**The write column of the rights matrix has exactly one non-empty row.** The AI layer may
write `AIArtifact`, `AISummary` and `ExtractionCandidate`, and nothing else.

| Object | Read | Write |
|---|---|---|
| Canonical clinical records | Yes, via `AIReadScope`, text labelled | **Never** |
| `Patient` — age, sex | Yes, as `AIPatientView` | Never |
| `Patient` — names, identifiers, contacts, address, date of birth | **No** | Never |
| `DataQualityFlag` | Yes, and must be surfaced | Never |
| `SourceReference` | Yes, and must be cited | Never |
| `Consent` | Not read by the agent; consumed by the gate | Never |
| `Coverage` | **No** — payment context is not clinical | Never |
| `AuditEvent` | **No** | Never; written by the system |
| `AIArtifact`, `AISummary` | Yes | **Yes — the only writable objects** |
| `ExtractionCandidate` | Yes | Yes — this is the suggestion channel |
| `Task` | Yes | No; may propose, with `status=proposed` |

An agent proposes a canonical record by writing an `ExtractionCandidate`. A human accepting
it is what creates the canonical record, and that record's provenance credits the extraction
while naming the accepting human as the one who vouched. The reverse link —
"which artifact produced this fact" — lives on `AIArtifact.produced`, a query against the AI
layer, because a back-pointer from canonical would break the one-way rule outright.

`execution` on an artifact is `Literal["local"]` with one legal value, so a cloud run is
unrepresentable rather than discouraged. What makes that hold is not the type: the field
could be lied to. It holds because `AIArtifact` is constructed only by the local-inference
adapter, and no public path takes `execution` as an argument. The prompt itself is never
stored — only its digest, alongside versioned `inputs`, so the prompt can be *reconstructed*
from canonical rather than duplicated outside canonical governance.

## What is deliberately not here

Named rather than discovered. The full list is `docs/model_design.md` §7.

- **The `EntityKind` registry and field-level `fields_read` recording.** Both degrade
  honestly: ids keep their prefixes without the registry, and `fields_read` stays `None`,
  which is a legal value meaning "assume the whole record".
- **General access control.** §10.3 gates the AI read path only.
- **Unit conversion inside trends.** Mismatched units are excluded with a visible reason
  rather than converted, which would need UCUM plus a conversion table.
- **Detecting transcribed external text.** A physician who pasted text is indistinguishable
  from one who typed it. The bulk case is explicit; this residue is named, not covered.
- **Detecting omission by a generation**, per the asymmetry above.
- **A retention policy for AI artifacts.** Pruning the AI layer destroys the ability to
  explain facts already accepted into canonical, which makes retention a governance question
  rather than an operational one.
